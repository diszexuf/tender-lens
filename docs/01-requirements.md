# Tender Lens — Требования к системе

Версия: 0.2 · Дата: 2026-11-14

## 1. Назначение

Tender Lens — система обоснования начальной (максимальной) цены договора (НМЦК) методом сопоставимых рыночных цен.
По текстовому описанию планируемой закупки система:

1. выделяет позиции закупки и их существенные характеристики;
2. ищет сопоставимые предложения в открытых источниках;
3. оценивает сопоставимость по характеристикам и приводит цены к сопоставимому виду;
4. исключает аномальные значения по явному правилу;
5. рассчитывает НМЦК и показатели разброса — или сообщает, что надёжных данных недостаточно;
6. формирует отчёт, из которого восстанавливается весь путь от описания закупки до итоговой цены.

Методическая основа — Методические рекомендации по применению методов определения НМЦК (Приказ Минэкономразвития России № 567). Перед релизом сверить с актуальной редакцией.

## 2. Термины

| Термин | Определение |
|---|---|
| Закупка | Входное описание планируемой закупки. Содержит одну или несколько позиций. |
| Позиция | Отдельный товар, работа или услуга в закупке, с количеством и единицей измерения. |
| Спецификация позиции | Структурированное представление позиции: наименование, код КТРУ/ОКПД2, типизированные характеристики, единица (ОКЕИ), количество. |
| Характеристика | Свойство позиции: атрибут, тип, оператор, значение, единица. Бывает **обязательной** (несовпадение исключает предложение) или **желательной** (влияет на оценку релевантности). |
| Источник | Внешний ресурс, из которого собираются данные. По роли бывает **ценовым** (даёт цены в расчёт) или **справочным** (подтверждает аналоги и характеристики, в расчёт цен не входит). |
| Адаптер | Программный модуль, реализующий доступ к источнику определённого типа. |
| Предложение (оффер) | Найденная цена на товар/работу/услугу с привязкой к источнику. |
| Снапшот | Сохранённая копия ответа источника на конкретный HTTP-запрос (страница выдачи, карточка товара или контракта). |
| Выборка | Множество предложений, включённых в расчёт по позиции. |
| CV | Коэффициент вариации: V = σ / x̄ · 100 %. |
| Расчёт | Запуск пайплайна по закупке. Имеет одну или несколько **версий**: каждая версия — оценка тех же собранных данных с определённой версией настроек. |

## 3. Границы MVP

**Входит в MVP:**
- текстовый ввод закупки, в том числе многопозиционной;
- источники: ЕИС (реестр контрактов, ценовой), конфигурируемый HTML-источник (ценовой), веб-поиск через SearXNG (ценовой), ГИСП (справочный);
- локальная LLM (Ollama);
- веб-интерфейс (Vue 3): ввод закупки, ход расчёта, отчёт, управление источниками, правилами и справочниками;
- выгрузка отчёта в PDF и XLSX;
- маскирование персональных данных на регулярных выражениях (модуль с тестами);
- запуск через Docker Compose.

**Не входит в MVP (заделы на развитие):**
- авторизация и роли;
- загрузка файлов ТЗ (DOCX/PDF);
- внешние LLM-провайдеры и NER-маскирование ФИО и адресов (Natasha) — подключаются вместе;
- специализированные адаптеры маркетплейсов и ЭТП (до этого подключаются как конфигурируемые HTML-источники);
- интеграция с ЕИС для публикации извещений.

## 4. Функциональные требования

Приоритет: **M** — обязательно для MVP, **S** — желательно для MVP, **C** — после MVP.

### FR-01. Ввод описания закупки

| ID | Требование | Приоритет |
|---|---|---|
| FR-01.1 | Пользователь вводит описание закупки свободным текстом (до 20 000 символов). | M |
| FR-01.2 | Описание может содержать несколько позиций (спецификацию). | M |
| FR-01.3 | Пользователь может указать дополнительные параметры: регион поставки, глубину поиска по контрактам (по умолчанию 3 года). | S |
| FR-01.4 | Система валидирует ввод: пустой текст и превышение лимита отклоняются с понятным сообщением. | M |
| FR-01.5 | Флаг `auto_run`: если включён, поиск запускается сразу после извлечения спецификации, без шага подтверждения. В API по умолчанию включён, в UI — выключен (пользователь проверяет спецификацию). | M |

### FR-02. Извлечение спецификации

| ID | Требование | Приоритет |
|---|---|---|
| FR-02.1 | LLM разбирает описание на позиции. Для каждой позиции извлекаются наименование, количество, единица измерения и характеристики. | M |
| FR-02.2 | Каждая характеристика типизирована: `name`, `type` (`number`, `range`, `enum`, `bool`, `text`), `operator` (`=`, `≥`, `≤`, `∈`, `between`), `value`, `unit`, `required` (обязательная / желательная). | M |
| FR-02.3 | Единица измерения позиции приводится к коду ОКЕИ по справочнику. Если однозначно привести нельзя, поле помечается для проверки пользователем. | M |
| FR-02.4 | LLM не генерирует коды КТРУ/ОКПД2. Модель формирует текстовый запрос, по нему система ищет код в справочнике КТРУ (поиск на ЕПЗ или загруженный справочник) и предлагает 1–3 кандидата. Код подтверждает пользователь; при `auto_run` берётся лучший кандидат с пометкой «не подтверждён». | S |
| FR-02.5 | Результат извлечения проходит валидацию по JSON-схеме. При невалидном ответе делаются повторные попытки (не более 3), затем выдаётся ошибка с исходным ответом модели и пустой формой для ручного ввода. | M |
| FR-02.6 | Пользователь может отредактировать спецификацию: до запуска поиска (если `auto_run` выключен) или после расчёта. Правка характеристик после расчёта запускает перерасчёт на собранных данных (FR-10.3); правка наименования или кода — новый сбор. | M |
| FR-02.7 | Исходный текст, ответ модели и итоговая спецификация сохраняются в расчёте. Правки пользователя видны в отчёте. | M |

### FR-03. Управление источниками

| ID | Требование | Приоритет |
|---|---|---|
| FR-03.1 | Источники хранятся в БД и управляются через веб-интерфейс (CRUD), без правки кода. | M |
| FR-03.2 | У источника есть тип адаптера (`eis`, `gisp`, `html`, `searxng`), **роль** (`price` / `reference`), название, базовый URL, признак активности, приоритет, таймаут, лимит запросов в минуту, максимальное число офферов на позицию (по умолчанию 20), категории ОКПД2, для которых источник применим (пусто — для всех), максимальный возраст цены (FR-07.8). | M |
| FR-03.3 | Для типа `html` задаются: шаблон URL поиска с подстановкой запроса, CSS/XPath-селекторы карточки, названия, цены, единицы, ссылки и характеристик, признак рендеринга JavaScript (Playwright), правила пагинации. Все селекторы необязательны: при их отсутствии работает цепочка извлечения FR-04.9. | M |
| FR-03.4 | Для типа `searxng` задаются allowlist и denylist доменов. По умолчанию allowlist содержит магазины и дистрибьюторов из списка источников кейса. | M |
| FR-03.5 | Кнопка «Проверить источник» выполняет тестовый запрос и показывает извлечённые предложения, использованный метод извлечения и ошибки. | M |
| FR-03.6 | Для каждого источника отображается состояние: время последнего успешного запроса, доля ошибок, статус circuit breaker. | S |
| FR-03.7 | Конфигурацию источников можно экспортировать и импортировать (JSON/YAML). | C |
| FR-03.8 | Новые типы адаптеров добавляются реализацией единого интерфейса и регистрацией без изменения ядра пайплайна. | M |

### FR-04. Поиск и сбор предложений

| ID | Требование | Приоритет |
|---|---|---|
| FR-04.1 | Для каждой позиции система формирует поисковые запросы под каждый активный источник: по наименованию, ключевым характеристикам и коду КТРУ/ОКПД2 (если он подтверждён или выбран). | M |
| FR-04.2 | Запросы к источникам выполняются параллельно, с ограничением скорости для каждого источника. | M |
| FR-04.3 | ЕИС: поиск по реестру контрактов со статусом «исполнение завершено» за настраиваемый период (по умолчанию 3 года). Из контракта берётся **цена за единицу конкретной позиции**, а не сумма контракта; если её нельзя выделить — исключение `missing_unit_price`. Контракты с начисленными неустойками исключаются (`contract_penalties`); если сведений нет — флаг `penalties_unknown` в отчёте. | M |
| FR-04.4 | Для каждого предложения сохраняются: источник, URL, дата и время получения (`fetched_at`), наименование, цена, валюта, статус НДС (`included`, `excluded`, `not_applicable`, `unknown`), единица измерения, количество в упаковке, характеристики (сырой текст), поставщик (наименование юрлица или пометка «ИП», ИНН), дата цены (дата контракта или публикации), условия поставки (если указаны), метод извлечения (`jsonld`, `microdata`, `selectors`, `llm`, `api`). | M |
| FR-04.5 | Ответ источника на каждый HTTP-запрос сохраняется как снапшот в объектном хранилище (S3, Garage) с хешем SHA-256. Оффер ссылается на один или несколько снапшотов (страница выдачи, карточка). Ссылки на снапшоты доступны из отчёта. | M |
| FR-04.6 | Если поля отсутствуют, предложение не отбрасывается молча: оно сохраняется с пометкой о недостающих полях и исключается с соответствующей причиной. | M |
| FR-04.7 | Ответы источников кэшируются (по умолчанию TTL 24 ч). Данные из кэша сохраняют исходное `fetched_at`. Пользователь может принудительно обновить данные. | S |
| FR-04.8 | Статус каждого источника в рамках расчёта (успех, пусто, ошибка, таймаут, структура изменилась, отключён) и текст ошибки фиксируются и попадают в отчёт. | M |
| FR-04.9 | Цепочка извлечения со страницы: JSON-LD `schema.org/Product`/`Offer` → microdata / OpenGraph → селекторы источника → LLM. Используется первый метод, давший цену. | M |
| FR-04.10 | Перед LLM-извлечением страница очищается от разметки и сжимается до фрагмента вокруг блока товара и цены (не более 2 000 токенов). | M |
| FR-04.11 | ГИСП работает как справочный источник: найденные отечественные аналоги и их характеристики выводятся в отдельном блоке отчёта и могут использоваться для уточнения поисковых запросов. В выборку цен и список исключённых они не попадают. | S |

### FR-05. Дедупликация и независимость цен

| ID | Требование | Приоритет |
|---|---|---|
| FR-05.1 | Дубли определяются по нормализованному URL (без UTM-меток и параметров сессии). | M |
| FR-05.2 | Дубли определяются по нечёткому совпадению связки «наименование + поставщик» при совпадении цены (порог сходства настраивается). | S |
| FR-05.3 | Для ЕИС дубли определяются по реестровому номеру контракта и номеру позиции. | M |
| FR-05.4 | Дубли не удаляются: они ссылаются на основное предложение и попадают в исключённые с причиной `duplicate`. | M |
| FR-05.5 | Одна цена на поставщика: если от одного поставщика (по ИНН, а при его отсутствии — по нормализованному наименованию) есть несколько цен на одну позицию, в выборку идёт самая свежая, остальные исключаются с причиной `same_supplier`. | M |

### FR-06. Оценка сопоставимости

| ID | Требование | Приоритет |
|---|---|---|
| FR-06.1 | Сопоставимость определяется по существенным характеристикам, а не только по названию. | M |
| FR-06.2 | **Предфильтр.** Офферы ранжируются по текстовому сходству с позицией (наименование, ключевые числа; rapidfuzz/BM25). Дальше проходят top-K (по умолчанию 15 на позицию, настраивается). Остальные исключаются с причиной `low_text_similarity` и остаются в отчёте. | M |
| FR-06.3 | **Извлечение атрибутов.** LLM извлекает из текста оффера значения характеристик спецификации в типизированном виде (тип и единица — как в FR-02.2) или `null`, если значения нет. Несколько офферов обрабатываются в одном вызове. Результат кэшируется по ключу «оффер + набор характеристик + модель + версия промпта». | M |
| FR-06.4 | **Сравнение кодом.** Каждая характеристика сравнивается компаратором своего типа: `number`/`range` — с учётом оператора и пересчёта единиц; `enum`/`bool` — с учётом справочника синонимов; `text` — нечёткое сравнение, а при неоднозначности — LLM. Результат: `match`, `mismatch` или `unknown` с пояснением. | M |
| FR-06.5 | `mismatch` по обязательной характеристике исключает оффер (`required_attr_mismatch`). `unknown` по обязательной характеристике снижает релевантность, но не исключает. | M |
| FR-06.6 | Релевантность (0–1) считается детерминированно: взвешенная доля совпадений (обязательные характеристики весят больше желательных, `unknown` = 0,5 от веса). Офферы ниже порога (по умолчанию 0,6) исключаются (`low_relevance`). Веса и порог настраиваются. | M |
| FR-06.7 | Регион поставки, если он указан, — желательная характеристика. Для услуг и работ его можно сделать обязательной; тогда несовпадение исключает оффер (`region_mismatch`). | S |
| FR-06.8 | У каждого предложения есть человекочитаемая причина включения или исключения. | M |
| FR-06.9 | Пользователь может вручную включить или исключить предложение с обязательным комментарием. Ручное решение привязано к паре «расчёт + оффер», применяется во всех последующих версиях расчёта и отмечается в отчёте как ручное. | S |

### FR-07. Нормализация

| ID | Требование | Приоритет |
|---|---|---|
| FR-07.1 | Цены приводятся к единице позиции по справочнику ОКЕИ с таблицей коэффициентов пересчёта. Если пересчёт невозможен — исключение `unit_incompatible`. Справочник редактируется через UI. | M |
| FR-07.2 | Учитывается фасовка и комплектация: цена упаковки делится на количество в упаковке. | M |
| FR-07.3 | Цены приводятся к виду «с НДС» по настраиваемой ставке: `excluded` → цена × (1 + ставка); `included` и `not_applicable` → как есть; `unknown` → как есть, с пометкой в отчёте. | S |
| FR-07.4 | Если стоимость доставки указана отдельно, она учитывается согласно настройке (включать или не включать). | C |
| FR-07.5 | Цены прошлых периодов (контракты ЕИС) индексируются к текущей дате по таблице индексов потребительских цен. Таблица заполняется при первом запуске и редактируется через UI. Коэффициент показывается в отчёте. | M |
| FR-07.6 | Каждое преобразование цены (исходная цена → коэффициенты → нормализованная цена) сохраняется и выводится в отчёте. | M |
| FR-07.7 | Цены не в рублях исключаются с причиной `currency_unsupported`. | M |
| FR-07.8 | Цены старше максимального возраста исключаются с причиной `stale_price`. Возраст задаётся в настройках источника: по умолчанию 3 года для ЕИС и 6 месяцев для остальных ценовых источников. | M |

### FR-08. Обработка выбросов и расчёт НМЦК

| ID | Требование | Приоритет |
|---|---|---|
| FR-08.1 | Выбросы определяются одним правилом, выбранным в настройках: **MAD** (по умолчанию: модифицированный z-score \|0,6745·(x − медиана)/MAD\| > 3,5), IQR (k = 1,5) или «без фильтрации». Правило и параметры фиксируются в версии расчёта. Исключённые получают причину `outlier_mad` / `outlier_iqr`. | M |
| FR-08.2 | При n < 5 фильтрация выбросов не применяется: на малых выборках она статистически ненадёжна. Это указывается в отчёте. | M |
| FR-08.3 | После фильтрации считается CV. Если CV ≤ порога (по умолчанию 33 %), выборка однородна. | M |
| FR-08.4 | Если CV > порога, позиция получает статус **«Неоднородная выборка»**: цена не формируется, автоматическая подрезка выборки по умолчанию не выполняется. Система показывает распределение цен и, если видит кластеры (например, разрыв между группами цен больше 2σ), подсказывает уточнить спецификацию или исключить предложения вручную (FR-06.9). | M |
| FR-08.5 | Опциональный режим «подрезка выборки» (по умолчанию выключен): наиболее удалённые от медианы значения исключаются по одному, пока CV не станет ≤ порога. Исключить можно не больше заданной доли выборки (по умолчанию 20 %) и не ниже минимального n. Каждый шаг протоколируется (`cv_trimming`), позиция получает статус **«Скорректированная выборка»**. | S |
| FR-08.6 | Минимальный размер выборки — 3 предложения (настраивается). Если выборка меньше, позиция получает статус **«Недостаточно надёжных данных»** с причиной и рекомендацией (запросить коммерческие предложения, ослабить требования, подключить источники). Цена не формируется. | M |
| FR-08.7 | Цена единицы позиции равна среднему арифметическому нормализованных цен выборки. Цена позиции равна цене единицы, умноженной на количество. НМЦК равна сумме цен позиций. Вычисления в `Decimal`, округление до копеек (half-up). | M |
| FR-08.8 | Для анализа выводятся n, минимум, максимум, среднее, медиана, σ, CV, а также границы правила выбросов. | M |

### 4.13. Справочник причин исключения

| Код | Этап | Текст для отчёта |
|---|---|---|
| `duplicate` | Дедупликация | Дубликат предложения №… |
| `same_supplier` | Дедупликация | Более ранняя цена того же поставщика |
| `missing_price` | Сбор | Цена не указана |
| `missing_unit_price` | Сбор (ЕИС) | Нельзя выделить цену за единицу позиции в контракте |
| `missing_data` | Сбор | Недостаточно данных для сравнения (перечень полей) |
| `currency_unsupported` | Нормализация | Цена не в рублях |
| `stale_price` | Нормализация | Цена старше допустимого возраста |
| `contract_penalties` | Сбор (ЕИС) | По контракту начислены неустойки |
| `low_text_similarity` | Предфильтр | Низкое текстовое сходство с позицией (не вошло в top-K) |
| `required_attr_mismatch` | Сопоставимость | Не совпадает обязательная характеристика: … |
| `region_mismatch` | Сопоставимость | Несопоставимый регион |
| `low_relevance` | Сопоставимость | Релевантность … ниже порога … |
| `unit_incompatible` | Нормализация | Единицу измерения нельзя привести к единице позиции |
| `outlier_mad` / `outlier_iqr` | Расчёт | Выброс по правилу … (границы …) |
| `cv_trimming` | Расчёт | Исключено при подрезке выборки, шаг … |
| `manual` | Ручное решение | Исключено пользователем: комментарий |

Информационные флаги (не исключают оффер): `penalties_unknown`, `vat_unknown`, `ktru_unconfirmed`, `outlier_filter_skipped_small_n`.

## 5. Нефункциональные требования

### NFR-01. Производительность

| ID | Требование |
|---|---|
| NFR-01.1 | Целевое время расчёта одной позиции при 4 активных источниках и top-K = 15 — не более 3 минут на целевом железе (NFR-07.1). Цифра уточняется по замеру на эталонном наборе (NFR-05.6). |
| NFR-01.2 | Отклик API на запросы, не запускающие пайплайн, — не более 500 мс (p95). |
| NFR-01.3 | Запросы к LLM ставятся в очередь (одновременно 1 запрос к GPU), чтобы не исчерпать видеопамять. Сетевой сбор идёт параллельно с этой очередью. |
| NFR-01.4 | Для экономии времени LLM: предфильтр top-K (FR-06.2), батчинг офферов (FR-06.3), извлечение без LLM там, где есть структурированные данные (FR-04.9), сжатие страниц (FR-04.10), кэш ответов LLM. |

### NFR-02. Надёжность и устойчивость

| ID | Требование |
|---|---|
| NFR-02.1 | Отказ, таймаут или изменение структуры страницы одного источника не прерывает расчёт. Ошибка фиксируется, остальные источники обрабатываются. |
| NFR-02.2 | Сетевые запросы выполняются с таймаутами и повторными попытками (экспоненциальная задержка с jitter, не более 3 попыток, только на сетевые ошибки, 5xx и 429). |
| NFR-02.3 | Если ошибки источника повторяются, срабатывает circuit breaker: источник временно пропускается, это отражается в статусе. |
| NFR-02.4 | Если при HTTP 200 и непустой странице ни один метод извлечения не нашёл офферов, источник получает отдельный статус `structure_changed`. |
| NFR-02.5 | Состояние расчёта хранится в БД. После перезапуска воркера незавершённые расчёты помечаются как прерванные и могут быть перезапущены. |

### NFR-03. Воспроизводимость и проверяемость

| ID | Требование |
|---|---|
| NFR-03.1 | В версии расчёта фиксируются: версия приложения, имя модели LLM, версии промптов, параметры генерации, версия настроек. |
| NFR-03.2 | Воспроизводимость обеспечивается **сохранёнными** ответами источников (снапшоты) и LLM, а не повторными вызовами: генерация LLM на GPU не гарантирует побитовой повторяемости даже при temperature = 0 и фиксированном seed. |
| NFR-03.3 | Этапы сравнения, нормализации и расчёта (FR-06.4 – FR-08) не используют LLM, кроме компаратора `text` при неоднозначности, и покрыты модульными тестами. |
| NFR-03.4 | По сохранённым предложениям, ответам LLM и параметрам расчёт можно повторить без обращения к источникам и к модели. |
