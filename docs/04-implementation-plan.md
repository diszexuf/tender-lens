# Tender Lens — План реализации

Версия: 0.1 · Дата: 2026-11-14

Связанные документы: [требования](01-requirements.md), [сценарии](02-use-cases.md), [архитектура](03-architecture.md).

## Принципы плана

- **Сначала сквозной путь, потом ширина.** После этапа 1 система должна проходить UC-01 от текста до отчёта, пусть с одним-двумя источниками. Каждый следующий этап расширяет работающую систему.
- **Каждый этап заканчивается рабочим `docker compose up`** и зелёными тестами — модульными и системными. Каждый новый эндпоинт сразу получает системный тест, а контракт `contracts/openapi.json` обновляется через `npm run gen:api`.
- **Детерминированное ядро — с тестами с первого дня:** компараторы, нормализация, выбросы, расчёт.
- **Эталонный набор растёт с проектом:** начинается на этапе 1 и используется для выбора модели и регресса.

Сроки в днях не указаны — их проставим, когда будет известна длительность хакатона и состав команды. Порядок этапов и критерии готовности от этого не меняются.

## Этап 0. Инфраструктура и каркас

**Цель:** чистый клон репозитория запускается одной командой.

**Задачи:**
- [x] `.gitignore`, `.env.example`, локальный `.env` (не в git).
- [x] `docker-compose.yml`: postgres 18, redis, garage, ollama (GPU), searxng, api, worker, web, init-jobs; healthchecks и `depends_on: condition: service_healthy`.
- [x] `docker-compose.cpu.yml` — оверрайд без GPU.
- [x] Init-скрипты (идемпотентные): настройка layout, ключа и бакетов Garage; `ollama pull $OLLAMA_MODEL`; `alembic upgrade head`.
- [x] `infra/searxng/settings.yml` с включённым JSON-форматом; `infra/nginx/default.conf` с прокси `/api` и поддержкой SSE (без буферизации).
- [x] Backend-каркас: uv-проект на Python 3.14, FastAPI, pydantic-settings, структурированные логи, SQLAlchemy async + Alembic (пустая начальная миграция), Taskiq-брокер, тестовая задача.
- [x] `GET /api/health`: БД, Redis, S3, Ollama (+ наличие модели), SearXNG.
- [x] Frontend-каркас: Vite + Vue 3 + TS, Router, Pinia, UI-библиотека, генерация клиента из OpenAPI, страница статуса сервисов.
- [x] **Проверка совместимости с Python 3.14:** установить и импортировать Playwright, asyncpg, extruct, rapidfuzz, openpyxl, taskiq, selectolax. Несовместимые — заменить и записать в архитектуру.
- [x] Проверка GPU: Ollama видит GPU в контейнере, замер скорости 2–3 моделей-кандидатов на простом промпте.
- [x] Линтеры и тесты: ruff, mypy (или pyright), pytest; eslint, vue-tsc.

**Итоги этапа 0:**
- Все зависимости совместимы с Python 3.14 (проверено `scripts/check_deps.py --browser` в образе worker, включая запуск Chromium и генерацию PDF).
- Frontend: TypeScript закреплён на 5.9 — TypeScript 6/7 пока не поддерживаются openapi-typescript и typescript-eslint.
- Модель по умолчанию — `qwen3:4b`: `qwen2.5:7b` не помещается в доступные ~5 ГБ VRAM (замер — в [архитектуре, §7](03-architecture.md#7-llm)).
- nginx резолвит `api` через DNS Docker при каждом запросе: иначе после пересоздания контейнера API — 502.
- Frontend на Vuetify 4; уязвимость minimatch в dev-зависимостях закрыта через `overrides` (`npm audit` — 0).
- Все образы закреплены как `тег@digest`.
- Системные тесты (`tests/system`, 22 проверки): health, контракт OpenAPI, nginx/SPA. Запускаются после каждого изменения: `docker compose --profile test run --rm --build system-tests`.

**Готово, когда:** `docker compose up` на чистой машине → `http://localhost:8080` показывает все сервисы зелёными; `pytest` и сборка фронтенда проходят.

## Этап 1. Сквозной MVP-путь

**Цель:** UC-01 и UC-02 работают от текста до отчёта в UI.

### 1.1. Данные и справочники
- [x] Модели и миграции: `calculation`, `position`, `source`, `source_run`, `snapshot`, `offer`, `offer_attributes`, `settings_version`, `calculation_version`, `offer_evaluation`, `position_result`, `llm_call`, `manual_decision`.
- [x] Справочники и seed: ОКЕИ (основные единицы) и коэффициенты пересчёта, стартовые синонимы, настройки по умолчанию (версия 1), источники по умолчанию.
- [x] Справочник причин исключения (код → шаблон текста) как enum в коде.

### 1.2. Эталонный набор (старт)
- [x] 8–10 закупок: картриджи, бумага, ручки, ноутбук, кабель, мебель, уборка, ремонт. Для каждой — ожидаемая спецификация и 5–10 офферов с разметкой «сопоставим / нет и почему».
- [x] Скрипт прогона эталона по этапам 1 и 6–7 с метриками (точность извлечения атрибутов, точность решений сопоставимости, время).

### 1.3. LLM-слой
- [x] `LLMProvider` + `OllamaProvider` (`format` = JSON Schema, повторы, запись в `llm_call`), семафор GPU.
- [x] `PIIMasker` на регулярных выражениях + тесты (провайдер внешний не подключаем, но модуль готов).
- [x] Промпты: разбор закупки, извлечение атрибутов (батч), извлечение оффера со страницы.
- [x] Выбор модели по эталону; значение по умолчанию в `.env.example` (`qwen3:4b`; сравнение с `qwen2.5:7b` на эталоне — этап 2).

### 1.4. Пайплайн
- [x] **SpecExtractor**: типизированная спецификация, ОКЕИ по справочнику, валидация, повторы.
- [~] **QueryBuilder**: поисковая фраза формируется LLM при разборе и правится в редакторе; шаблоны и синонимы для запросов — этап 2.
- [x] **Collector**: `SourceAdapter`, `AdapterRunner` (таймаут, ретраи, статусы ошибок), HTTP-клиент с SSRF-guard, кэш с исходным `fetched_at`, снапшоты в S3 на каждый запрос.
- [x] **Цепочка извлечения**: JSON-LD/microdata (extruct) → селекторы → LLM; очистка и сжатие страницы.
- [~] **Адаптер `eis`**: поиск в реестре контрактов, карточка контракта, цена за единицу позиции, поставщик, дата, неустойки/флаг; тесты парсера на синтетических страницах. **Не проверен на живых данных:** ЕПЗ недоступна из сети разработки (блокирует зарубежные IP).
- [x] **Адаптер `html`**: шаблон URL, селекторы (необязательные), `render_js` через Playwright. Один-два магазина из списка источников, настроенные через seed.
- [x] **Deduplicator**: канонизация URL, ЕИС-ключ, одна цена на поставщика.
- [x] **Prefilter**: rapidfuzz, top-K, отсев по валюте, возрасту, отсутствию цены.
- [x] **AttributeExtractor**: батчи, кэш в `offer_attributes`.
- [x] **Matcher**: компараторы `number`, `range`, `enum`, `bool`, `text` (fuzzy), пересчёт единиц, синонимы, скоринг, порог. Модульные тесты на каждый компаратор.
- [x] **Normalizer**: ОКЕИ, фасовка, протокол шагов. Тесты.
- [x] **PriceCalculator**: MAD/IQR, правило n < 5, CV, статусы `ok` / `heterogeneous` / `insufficient_data`, `Decimal`. Тесты, включая граничные случаи.
- [x] Оркестратор: задачи Taskiq `extract_spec`, `run_pipeline`; статусы расчёта; события в Redis pub/sub; `auto_run`.

### 1.5. API и UI
- [x] API: создание расчёта, получение, правка спецификации, запуск, SSE, отчёт в JSON, health.
- [x] UI «Новый расчёт»: ввод текста, переключатель проверки спецификации, редактор спецификации.
- [x] UI «Расчёт»: прогресс по этапам и источникам; отчёт — итог, позиции со статусами, включённые и исключённые с причинами, атрибуты со статусом сравнения, статистика, ссылки на снапшоты.
- [x] UI «История»: список расчётов.

**Сверх плана (из-за ограничений источников):**
- [x] **Адаптер `searxng`** перенесён из этапа 2: страницы поиска большинства магазинов закрыты `robots.txt`, карточки товаров находятся через поисковые системы.
- [x] Общий `CardExtractor` для HTML-источников и веб-поиска; проверка цены LLM по тексту страницы.
- [x] Скрипт проверки источника `scripts/probe_source.py` (основа кнопки «Проверить источник», этап 2).
- [x] Системные тесты API расчётов (`tests/system/test_calculations.py`), полный прогон — маркер `slow`.

**Итоги этапа 1:**
- Сквозной путь работает в UI и API: разбор → сбор (ЭТМ, веб-поиск; ЕИС — таймаут) → сопоставление → нормализация → расчёт → отчёт. Кабель ВВГнг(А)-LS (UC-01): 1–4 мин на позицию.
- Эталонный набор (9 закупок, `qwen3:4b`): позиции 100 %, количество 90 %, ОКЕИ 100 %, характеристики найдены 90,5 % / точно 76,2 %, решения о сопоставимости 85,7 %, разбор 6,7 с.
- Тесты: 124 модульных, 37 системных.
- Решения по живым прогонам: одна цена поставщика — только на тот же товар; название товара важнее извлечения (совпадение и противоречие по кодам); неоднозначная фасовка из названия выбирается по ценам соседей; правило выбросов, отмечающее > 25 % выборки, означает неоднородность.

**Известные ограничения (переходят в этап 2):**
- ЕИС не проверена на живых данных — нужен доступ из российской сети или прокси.
- Нормализация фасовок для позиций в упаковках (UC-02): коробки по 5 пачек, упаковки 70 и 100 шт, ошибочная фасовка от LLM. Расчёт честно даёт «неоднородная выборка», но цену не формирует.
- Строгость сравнения кодов: «ВВГ-Пнг(А)-LS» не считается «ВВГнг(А)-LS» — решается справочником синонимов.

**Готово, когда:** пример UC-01 и UC-02 из сценариев проходит в UI до отчёта; UC-04A (мало данных) даёт «Недостаточно надёжных данных», а не цену; падение одного источника не прерывает расчёт; модульные тесты ядра проходят; эталонный прогон показывает метрики.

## Этап 2. Расширение и проверяемость

**Цель:** источники добавляются из UI, расчёт полный по методике, отчёт выгружается.

- [x] **Реестр типов адаптеров** и `GET /api/source-types` с JSON Schema; UI «Источники»: список, форма по схеме, включение/отключение, «Проверить источник» с методом извлечения (UC-09, UC-10).
- [ ] **Адаптер `searxng`**: JSON API, allowlist/denylist доменов, загрузка страниц и цепочка извлечения.
- [ ] **Нормализация, полный объём**: статусы НДС и приведение к «с НДС»; индексация по таблице ИПЦ (seed + редактирование); возраст цены `stale_price`.
- [ ] Регион как атрибут, `region_mismatch` (UC-03).
- [ ] **Выгрузки**: HTML-шаблон отчёта; PDF через Playwright в worker; XLSX с формулами (среднее, σ, CV по строкам выборки); задача `render_export`, хранение в S3, presigned URL.
- [ ] **Ручные решения**: API и UI с обязательным комментарием; новая версия расчёта; решение применяется во всех последующих версиях (UC-06).
- [ ] Подсказки по кластерам для статуса `heterogeneous` (UC-04B).
- [ ] Отмена расчёта, восстановление прерванных после рестарта воркера.
- [ ] Эталонный набор до 15–20 закупок, включая услуги и узкоспециальные товары.

**Готово, когда:** новый магазин добавляется через UI и даёт офферы в расчёте без изменения кода; PDF и XLSX выгружаются, формулы XLSX дают те же числа, что и UI; UC-03 работает с индексацией и регионом.

## Этап 3. Устойчивость и гибкость

**Цель:** закрыть критерии универсальности и устойчивости, добавить развитые возможности.

- [ ] **Версии и перерасчёт** (UC-08): `POST /recalculate`, сравнение версий в UI; правка атрибутов после расчёта → перерасчёт, правка наименования/КТРУ → новый сбор (UC-05).
- [ ] **Настройки и справочники в UI** (UC-11): правила с версионированием; редакторы ОКЕИ, индексов, синонимов.
- [ ] **Circuit breaker** в Redis, rate limit, отображение здоровья источников (FR-03.6); статус `structure_changed`.
- [ ] **ГИСП** как справочный источник, блок в отчёте, дополнение поисковых запросов аналогами.
- [ ] **КТРУ**: `GET /api/ktru/search`, кандидаты в редакторе спецификации, флаг `ktru_unconfirmed`; использование кода в адаптере ЕИС.
- [ ] Режим подрезки выборки (опционально, ≤ 20 %), статус `ok_adjusted`.
- [ ] Audit trail в JSON (FR-09.5).
- [ ] Нагрузочный прогон эталона: фиксация времени на позицию, уточнение NFR-01.1.

**Готово, когда:** отключение сети или поломка селекторов одного источника видны в UI и отчёте с понятным статусом; смена порога CV из UI создаёт новую версию расчёта без повторного сбора и вызовов LLM; новая категория из эталона проходит без правок кода.

**Цель:** решение запускается и понимается без участия команды.

- [ ] README: требования к окружению (включая GPU и WSL2 на Windows), команды запуска и остановки, зависимости, переменные окружения, внешние сервисы, раздел «если не запускается».
