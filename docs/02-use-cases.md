# Tender Lens — Пользовательские сценарии

Версия: 0.2 · Дата: 2026-11-14

## Акторы

| Актор | Описание |
|---|---|
| Специалист по закупкам | Готовит обоснование НМЦК: вводит описание закупки, проверяет выборку, выгружает отчёт. |
| Администратор | Настраивает источники, правила расчёта и справочники. В MVP авторизации нет, поэтому это та же роль, что и специалист, но в другом разделе интерфейса. |
| Внешняя система | Вызывает API напрямую (`auto_run = true`), например автотесты или интеграция. |
| Внешние источники | ЕИС, ГИСП, сайты поставщиков, SearXNG. |
| LLM | Локальная модель в Ollama. |

## UC-01. Расчёт НМЦК по однопозиционной закупке товара

**Цель:** получить обоснованную НМЦК по одному товару.
**Предусловия:** система запущена, активен хотя бы один ценовой источник, модель LLM загружена.

**Основной поток:**
1. Специалист открывает «Новый расчёт» и вводит описание закупки.
2. Система извлекает спецификацию (FR-02): позиции, типизированные характеристики, единицу ОКЕИ, кандидатов кода КТРУ.
3. Специалист проверяет спецификацию (UC-05) и запускает поиск. Если включён `auto_run`, шаг пропускается.
4. Система показывает прогресс: этап пайплайна и статус каждого источника.
5. Система собирает предложения, удаляет дубли и повторные цены одного поставщика, отбирает top-K по текстовому сходству, извлекает и сравнивает характеристики, нормализует цены, фильтрует выбросы и считает НМЦК.
6. Специалист видит отчёт: итоговую цену, включённые и исключённые предложения с причинами, показатели разброса, справочный блок ГИСП.
7. Специалист выгружает отчёт в PDF или XLSX.

**Пример входа:**
```
Картридж лазерный для принтеров HP LaserJet Pro P1102/M1132, ресурс не менее 1600 страниц,
цвет чёрный, оригинальный или совместимый. Количество — 50 шт.
```

**Извлечённая спецификация (фрагмент):**
```
Позиция 1: Картридж лазерный · 50 шт (ОКЕИ 796)
  совместимость  enum   ∈ {HP LaserJet Pro P1102, HP LaserJet Pro M1132}   обязательная
  ресурс         number ≥ 1600 стр.                                         обязательная
  цвет           enum   = чёрный                                            обязательная
  тип            enum   ∈ {оригинальный, совместимый}                       желательная
```

**Ожидаемый результат (пример структуры, числа условные):**
```
Позиция 1. Картридж лазерный, чёрный, ресурс ≥1600 стр., совместим с HP P1102/M1132 — 50 шт
  Найдено ценовых предложений: 16 (ЕИС — 7, HTML-источники — 5, веб-поиск — 4)
  Справочно (ГИСП): 2 отечественных аналога
  Исключено: 9
    • 3 — дубликат
    • 3 — не совпадает обязательная характеристика (ресурс 1000 стр.; цвет — голубой; модель CE278A)
    • 1 — недостаточно данных (не указана цена)
    • 1 — более ранняя цена того же поставщика
    • 1 — выброс по правилу MAD (|z| = 4,2 > 3,5)
  Выборка: n = 7, min = 1 150,00, max = 1 890,00, медиана = 1 470,00,
           среднее = 1 482,14, σ = 268,40, CV = 18,1 % — выборка однородна
  Цена за единицу = 1 482,14 ₽; цена позиции = 1 482,14 × 50 = 74 107,00 ₽
НМЦК = 74 107,00 ₽ (с НДС)
```
У каждого предложения в таблице есть источник, ссылка, снапшот, дата получения, поставщик, характеристики со статусом сравнения (✓ / ✗ / ?), исходная цена, шаги нормализации, нормализованная цена, релевантность и причина включения.

**Альтернативные потоки:**
- 2a. Модель не смогла извлечь спецификацию: система показывает ошибку и пустую форму, спецификацию можно заполнить вручную.
- 5a. Недостаточно данных или выборка неоднородна: см. UC-04.
- 5b. Источник недоступен: см. UC-12.

**Связанные требования:** FR-01, FR-02, FR-04 – FR-09.

## UC-02. Расчёт НМЦК по многопозиционной закупке

**Цель:** получить НМЦК закупки как сумму цен по позициям.

**Основной поток:**
1. Специалист вводит спецификацию из нескольких позиций.
2. Система выделяет каждую позицию отдельно, с количеством и единицей.
3. Дальше UC-01 выполняется для каждой позиции.
4. В отчёте показан расчёт по каждой позиции и итог: НМЦК = Σ (цена единицы × количество).

**Пример входа:**
```
Поставка канцелярских товаров:
1. Бумага офисная А4, 80 г/м², белизна не менее 146% CIE, 500 листов в пачке — 200 пачек.
2. Ручка шариковая синяя, толщина линии 0,7 мм — 500 шт.
3. Скрепки металлические 28 мм, упаковка 100 шт — 100 упаковок.
```

**Ожидаемый результат (числа условные):**
```
| № | Позиция                   | Ед.  | Кол-во | n | CV, %  | Статус | Цена ед., ₽ | Сумма, ₽   |
|---|---------------------------|------|--------|---|--------|--------|-------------|------------|
| 1 | Бумага А4 80 г/м²         | пач. | 200    | 9 | 12,4   | ok     | 389,50      | 77 900,00  |
| 2 | Ручка шариковая синяя 0,7 | шт   | 500    | 8 | 21,7   | ok     | 18,40       | 9 200,00   |
| 3 | Скрепки 28 мм, 100 шт     | уп.  | 100    | 6 | 15,2   | ok     | 47,30       | 4 730,00   |
НМЦК = 91 830,00 ₽
```
Если цену ручки нашли только за упаковку по 50 шт, в отчёте видно приведение: «цена упаковки 920,00 ₽ / 50 шт = 18,40 ₽/шт».

**Альтернативные потоки:**
- 4a. По одной из позиций цена не сформирована: итог помечается как **неполный**, позиция выводится отдельно со статусом и рекомендацией (FR-08.9).

**Связанные требования:** FR-01.2, FR-02.1, FR-07.1, FR-07.2, FR-08.7, FR-08.9.

## UC-03. Расчёт НМЦК по закупке услуги

**Цель:** показать, что система работает не только с товарами.

**Основной поток:** как в UC-01. Отличия:
- единица измерения услуги по ОКЕИ (м², час, месяц, условная единица);
- основной источник — контракты ЕИС, так как публичных прайсов на услуги мало;
- существенные характеристики: объём, периодичность, состав работ; регион — обязательная характеристика (FR-06.7);
- цены контрактов прошлых лет индексируются (FR-07.5).

**Пример входа:**
```
Оказание услуг по ежедневной уборке офисных помещений площадью 1200 м², г. Москва,
срок оказания услуг — 12 месяцев.
```

**Ожидаемый результат:** цена за 1 м² в месяц по сопоставимым контрактам ЕИС, проиндексированная к текущей дате, × 1200 м² × 12 мес. В отчёте видны коэффициенты индексации. Контракты из других регионов исключены с причиной `region_mismatch`; контракты, где нельзя выделить цену за м², — с причиной `missing_unit_price`.

**Связанные требования:** FR-04.3, FR-06.7, FR-07.1, FR-07.5.

## UC-04. Недостаточно данных или неоднородная выборка

**Цель:** не выдавать необоснованную цену.

**Вариант A. Недостаточно данных:**
1. После сбора и фильтрации в выборке меньше минимального числа предложений (по умолчанию 3).
2. Позиция получает статус «Недостаточно надёжных данных», цена не формируется.
3. В отчёте указаны причина («найдено 2 сопоставимых предложения из 3 необходимых»), всё найденное и исключённое и рекомендации: запросить коммерческие предложения, ослабить требования спецификации, подключить источники.

**Пример входа:**
```
Анализатор спектра портативный, диапазон 9 кГц – 44 ГГц, динамический диапазон не менее 160 дБ — 1 шт.
```
**Ожидаемый результат:** «НМЦК не сформирована: недостаточно надёжных данных» и полный список найденного с причинами исключения.

**Вариант B. Неоднородная выборка:**
1. После фильтрации выбросов CV > 33 %.
2. Позиция получает статус «Неоднородная выборка», цена не формируется. Автоматическая подрезка выборки по умолчанию выключена (FR-08.4).
3. Система показывает распределение цен и, если видит кластеры, подсказывает причину, например: «две группы цен: 900–1 200 ₽ (совместимые) и 3 800–4 500 ₽ (оригинальные) — уточните характеристику „тип“».
4. Специалист уточняет спецификацию (UC-05) или исключает предложения вручную (UC-06), и система пересчитывает позицию.

**Альтернативный поток B-2a.** В настройках включён режим подрезки (FR-08.5): система исключает не больше 20 % выборки, пока CV не станет ≤ 33 %. Позиция получает статус «Скорректированная выборка», каждый шаг виден в отчёте.

**Связанные требования:** FR-08.4 – FR-08.6, FR-08.9.

## UC-05. Проверка и корректировка спецификации

**Цель:** исправить ошибки извлечения.

**Основной поток (до поиска, `auto_run` выключен):**
1. После извлечения система показывает позиции и характеристики в редактируемой форме: тип, оператор, значение, единица, обязательность.
2. Для каждой позиции система предлагает 1–3 кандидата кода КТРУ, найденных по справочнику (FR-02.4). Специалист выбирает код или оставляет поле пустым.
3. Специалист правит значения, добавляет или удаляет характеристики, количество и единицу.
4. Специалист запускает поиск по итоговой спецификации.

**Альтернативный поток (после расчёта):**
- 1a. Специалист открывает спецификацию завершённого расчёта и меняет характеристики. Система выполняет перерасчёт на собранных данных и создаёт новую версию (UC-08).
- 1b. Если изменены наименование или код КТРУ, система предупреждает, что нужен новый сбор, и запускает его по подтверждению.

В отчёте видны исходная и итоговая спецификация, правки отмечены.

**Связанные требования:** FR-02.4, FR-02.6, FR-02.7, FR-09.3 (б).

## UC-06. Ручное включение или исключение предложения

**Цель:** дать специалисту право окончательного решения с сохранением прозрачности.

**Основной поток:**
1. Специалист открывает отчёт и выбирает предложение.
2. Специалист нажимает «Исключить» (или «Включить» для исключённого) и указывает обязательный комментарий.
3. Система создаёт новую версию расчёта: пересчитывает выбросы, CV и цену позиции без повторного сбора.
4. В отчёте решение помечено как ручное, с комментарием и временем. Решение сохраняется и в следующих версиях расчёта.

**Альтернативный поток:**
- 2a. Комментарий не указан: действие не выполняется.

**Связанные требования:** FR-06.9, FR-08, FR-10.3.

## UC-07. Просмотр истории и выгрузка отчёта

**Основной поток:**
1. Специалист открывает «Историю расчётов».
2. Система показывает список: дата, краткое описание, статус, НМЦК, признак неполноты.
3. Специалист находит расчёт поиском по тексту и открывает отчёт нужной версии.
4. Специалист выгружает отчёт в PDF или XLSX и открывает снапшот исходной страницы любого предложения.

**Связанные требования:** FR-09, FR-10.2.

## UC-08. Перерасчёт с другими правилами на тех же данных

**Цель:** понять, как правила влияют на результат, без повторного сбора.

**Основной поток:**
1. Специалист открывает расчёт в любом завершённом статусе, включая «недостаточно данных» и «неоднородная выборка», и нажимает «Перерасчитать».
2. Специалист меняет параметры: правило выбросов, порог CV, порог релевантности, top-K.
3. Система выполняет этапы оценки на сохранённых предложениях с учётом ручных решений. Извлечённые атрибуты берутся из кэша, LLM повторно не вызывается (кроме офферов, впервые попавших в top-K).
4. Создаётся новая версия расчёта со ссылкой на версию настроек. Специалист сравнивает версии.

**Связанные требования:** FR-10.3, FR-12.2, NFR-03.4.

## UC-09. Добавление нового HTML-источника без изменения кода

**Цель:** подключить новый сайт поставщика или магазин через интерфейс.

**Основной поток:**
1. Администратор открывает «Источники» и нажимает «Добавить», тип — `html`, роль — «ценовой».
2. Администратор заполняет название, базовый URL, шаблон URL поиска (например, `https://shop.example.ru/search?q={query}`), признак JS-рендеринга, лимиты, таймаут и максимальный возраст цены. Селекторы можно не заполнять.
3. Администратор нажимает «Проверить источник» и вводит тестовый запрос.
4. Система выполняет запрос и показывает таблицу извлечённых предложений и метод извлечения (JSON-LD, microdata, селекторы или LLM).
5. Если результат неполный, администратор дописывает селекторы и повторяет проверку.
6. Администратор сохраняет и активирует источник. В следующих расчётах источник используется автоматически.

**Альтернативные потоки:**
- 4a. Ни один метод не нашёл офферов: система показывает ошибку «структура страницы не распознана» и фрагмент HTML для отладки.
- 2a. URL указывает на внутренний адрес: сохранение запрещено (NFR-04.4).

**Связанные требования:** FR-03.1 – FR-03.5, FR-04.9, NFR-04.4.

## UC-10. Управление источниками и мониторинг их состояния

**Основной поток:**
1. Администратор открывает список источников: тип, роль, статус, последний успешный запрос, доля ошибок, состояние circuit breaker.
2. Администратор включает или отключает источник, меняет приоритет, лимиты, применимые категории ОКПД2, для SearXNG — allowlist доменов.
3. Изменения применяются к новым расчётам.

**Связанные требования:** FR-03.2, FR-03.4, FR-03.6.

## UC-11. Настройка правил расчёта и справочников

**Основной поток:**
1. Администратор открывает «Настройки».
2. Администратор меняет порог CV, минимальный размер выборки, правило выбросов, режим подрезки, top-K, порог релевантности, веса характеристик, ставку НДС и глубину поиска по ЕИС.
3. Администратор редактирует справочники: единицы ОКЕИ и коэффициенты пересчёта, индексы цен, синонимы атрибутов и значений.
4. Система сохраняет новую версию настроек. Новые расчёты и перерасчёты ссылаются на неё.

**Пример:** администратор добавляет синоним «yield» → «ресурс». В следующем расчёте оффер с характеристикой «Yield: 1600 pages» сопоставляется с требованием «ресурс ≥ 1600 стр.» как `match`.

**Связанные требования:** FR-12.

## UC-12. Работа при недоступности источника

**Цель:** расчёт завершается, даже если часть источников отказала.

**Основной поток:**
1. Во время сбора источник отвечает ошибкой, не отвечает или меняет структуру страницы.
2. Система делает повторные попытки по политике NFR-02.2.
3. Если попытки не помогли, источник получает статус с типом ошибки (сеть, таймаут, HTTP-код, `structure_changed`), и расчёт продолжается без него.
4. В отчёте указано, какие источники недоступны и почему.
5. Если ошибки повторяются, срабатывает circuit breaker и источник временно пропускается в следующих расчётах (UC-10 показывает это администратору).

**Альтернативный поток:**
- 3a. Недоступны все ценовые источники: позиции получают статус «Недостаточно надёжных данных» со списком ошибок (UC-04, вариант A).

**Связанные требования:** FR-04.8, NFR-02.

## UC-13. Расчёт через API без участия пользователя

**Цель:** получить результат одним вызовом, без шага подтверждения спецификации.

**Основной поток:**
1. Внешняя система вызывает `POST /api/calculations` с текстом закупки (`auto_run` по умолчанию `true`).
2. Система извлекает спецификацию, выбирает лучший кандидат кода КТРУ с флагом `ktru_unconfirmed` и сразу запускает сбор и расчёт.
3. Внешняя система получает статус через `GET /api/calculations/{id}` или SSE и забирает отчёт в JSON.

**Связанные требования:** FR-01.5, FR-02.4, FR-09.5.
